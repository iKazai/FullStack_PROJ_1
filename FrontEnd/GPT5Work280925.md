## Comment ça marche côté front
- L’URL du backend est lue via la variable `NEXT_PUBLIC_API_BASE` (définie dans `.env.local`). Par défaut: `http://localhost:8080`.
- `fetchPlayers(params)` construit l’URL `GET /players` en ajoutant les paramètres non vides (ex: `?teamName=...&position=...`).
- Dans page.tsx, on lit tes sélections, on forme `params` et on appelle `fetchPlayers(params)`. On affiche les joueurs dans une `<ul>`.

Paramètres supportés par le backend:
- teamName, lastName, firstName, position, college, country, jerseyNumber, teamCity, height, weight, draftYear

Note: aujourd’hui, le backend accepte 1 valeur par filtre (string/number). Dans page.tsx, on envoie seulement le premier élément sélectionné pour chaque filtre (ex: `selectedTeams[0]`). Si tu veux un support multi-valeurs (ex: plusieurs équipes), on pourra: 
- Soit changer le backend pour accepter des listes (ex: `teamName=...&teamName=...`), 
- Soit créer un endpoint POST avec un body JSON, 
- Soit combiner côté front les valeurs en chaîne (ex: séparées par des virgules) et adapter le service.

## Points d’attention
- CORS: j’ai activé `@CrossOrigin(origins = {"http://localhost:3000"})` sur `PlayerController`. Si ton front tourne sur un autre host/port, ajuste cette origine.
- Schéma JSON: le backend renvoie des clés en snake_case (ex: `player_first_name`), qu’on typait bien côté front (type `Player`).
- Multi-filtres: aujourd’hui un seul élément pris par filtre (ex: `selectedTeams[0]`). Dis-moi si tu veux qu’on fasse évoluer le backend pour les tableaux.
- URL backend: si ton backend n’est pas sur `http://localhost:8080`, change `NEXT_PUBLIC_API_BASE` dans .env.local.
